# 코드 리뷰

목표는 지적 개수를 늘리는 게 아니라 **실제로 무언가를 깨뜨리거나 깨뜨릴 수 있는 것**을
찾아 근거와 함께 내놓는 것이다.

이 기준이 중요한 이유: 지적이 20개 달린 리뷰는 읽히지 않고 통째로 무시된다. 그중 3개가
진짜 버그였더라도 마찬가지다. 취향 지적에 섞여 진짜 결함이 묻히면 리뷰는 오히려
해롭다. **적게 쓰고, 각각을 실행으로 증명하는 편이 실제로 고쳐진다.**

## 1. 리뷰 전에 범위를 확정한다

대상이 지정되지 않았으면 먼저 확인한다:

```bash
git status
git diff                  # 워킹트리 변경
git diff --stat HEAD~1    # 직전 커밋 대비
```

그리고 **무엇을 리뷰할지 한 줄로 밝힌 뒤 시작한다.** "변경분 전체"인지 "특정 모듈"인지
정하지 않고 읽기 시작하면 범위가 계속 넓어져 결론이 안 난다.

변경분 리뷰라면 **바뀐 줄만 보지 않는다.** 바뀐 함수의 호출자, 그 함수가 반환하는
자료구조를 소비하는 쪽, 대응 테스트까지 함께 읽는다. 대부분의 실제 결함은 바뀐 줄이
아니라 **바뀐 줄과 안 바뀐 줄의 경계**에 있다.

## 2. 이 저장소의 확정된 사실

아래는 이 스킬을 쓴 시점의 기록이다. **실제 파일과 어긋나면 실제 파일을 따르고, 어긋난
사실을 보고에 남긴다.** 문서보다 코드가 최신이다.

### 실행

```bash
uv run pytest                        # 전체 테스트
uv run python -m vibe_coding.stats   # 커밋 통계 실행
uv run python main.py                # 루트 진입점
uv run vibe-coding                    # 콘솔 스크립트 진입점 (다른 함수다)
```

`src/` 레이아웃이라 `vibe_coding` import는 `.venv`의 editable 설치(`vibe_coding.pth`)를
통해서만 해석된다. **맨 `pytest`나 맨 `python`은 `ModuleNotFoundError`로 실패한다** —
이건 코드 결함이 아니라 실행 방법 문제다. 이걸 결함으로 올리지 않는다.

### 구조적으로 헷갈리는 지점

- **두 개의 `main()`.** 루트 `main.py`와 `[project.scripts]`의 `vibe_coding:main`은 서로
  다른 함수다. 루트 `main.py`는 `src/` 밖이라 설치 패키지에 포함되지 않는다.
- **이중 재노출.** `<pkg>/<module>.py` → `<pkg>/__init__.py` → `vibe_coding/__init__.py`.
  테스트가 `from vibe_coding import X` 평탄 경로에 의존한다. 새 모듈이 두 `__init__.py`와
  각 `__all__`을 모두 거치지 않으면 조용히 깨진다.
- **TDD 훅.** `.claude/settings.json`이 `Write|Edit`에 `tdd_guard.py`(PreToolUse)와
  `tdd_pytest.py`(PostToolUse)를 건다. `src/` 수정은 대응 테스트와 Red 기록을 요구한다.
- **린터·포매터·타입 힌트가 없다.** 이건 의도된 현재 상태다.

## 3. 무엇을 결함으로 볼 것인가

지적을 세 등급으로 나눈다. **등급을 섞지 않는 것이 이 스킬의 핵심이다.**

### 결함 — 고쳐야 한다

- 틀린 계산 결과, 조용한 데이터 손실, 잘못된 예외 타입
- 특정 입력에서 터지는 크래시 (`KeyError`, `IndexError`, `ValueError`)
- **계약 변경**: 공개 함수의 반환 자료구조·키·타입이 바뀌었는데 호출자나 테스트가
  따라오지 않음
- 문서(`CLAUDE.md`, `README.md`)에 적힌 명령·경로·동작이 지금 사실이 아님
- 테스트가 **버그를 고정**하고 있음 (잘못된 동작에 맞춰 통과시킴)
- 재노출 누락으로 평탄 import 경로가 깨짐

### 의심 — 확인이 필요하다

지금은 통과하지만 전제가 깨지면 무너지는 것. **단정하지 말고 전제를 명시한다.**

- 명시되지 않은 정렬·순서에 기대는 로직 (예: `git log` 기본 정렬)
- 입력 형식에 대한 암묵적 가정 (구분자가 데이터 안에 나타날 가능성 등)
- 테스트가 검증하지 않는 분기

### 선택 사항 — 안 고쳐도 된다

한 줄씩만 쓴다. **아래는 이 저장소에서 결함이 아니다:**

- 타입 힌트 없음, 포매팅 불일치, 독스트링 부족
- 계층 분리·추상화 도입·예외 클래스 체계 같은 재설계 제안
- 린터 도입, `parametrize` 도입 등 새 도구·스타일 제안

학습용 소규모 저장소라는 맥락을 지킨다. **요청받지 않은 확장은 범위 밖이다.**

## 4. 근거 없는 지적은 쓰지 않는다

- **모든 지적에 `파일:줄`을 붙인다** (`src/vibe_coding/stats/gitstats.py:34` 형식).
- **실행으로 확인할 수 있는 것은 실행한다.** "아마 실패할 것이다"는 리뷰가 아니다.
  실제 명령과 그 출력을 근거로 쓴다.
- 크래시를 주장하려면 **재현 입력을 만들어 실제로 돌려본다:**

  ```bash
  uv run python -c "from vibe_coding import GitStats; print(GitStats().parse('...'))"
  ```

- 재현하지 못한 것은 **결함이 아니라 의심**으로 내린다. 확신의 정도를 등급으로 표현한다.
- **찾지 못한 것을 찾은 것처럼 쓰지 않는다.** 결함이 없으면 "결함 없음"이라고 쓴다.
  빈손으로 돌아오는 것은 실패가 아니다. 없는 결함을 지어내는 것이 실패다.

## 5. 이 저장소에서 실제로 나오는 결함 유형

체크리스트로 훑되, 해당 없으면 넘어간다. 억지로 채우지 않는다.

1. **계약 변경의 파급.** 반환 dict의 키가 바뀌었는가? 그렇다면 그 dict를 소비하는 모든
   곳(다른 메서드, `run()`, 테스트)이 따라왔는가? `grep`으로 호출자를 전부 찾는다.
2. **파싱 가정.** 구분자로 필드를 나누는 코드는 **데이터 안에 구분자가 들어올 때** 어떻게
   되는가? 필드 수가 어긋난 줄이 조용히 버려지지는 않는가?
3. **딕셔너리 조회.** `d[k]` 형태가 있으면 `k`가 항상 존재함을 보장하는 근거를 찾는다.
   같은 입력에서 파생된 두 dict라면 안전하다 — 그 근거를 확인하고 넘어간다.
4. **순서 의존.** "가장 최근 것"·"첫 번째 것"을 고르는 로직은 입력 순서를 전제한다.
   그 순서를 누가 보장하는지 확인한다. 보장이 코드 밖(외부 명령의 기본 동작)에 있으면
   **의심**으로 올린다.
5. **테스트와 구현의 정렬.** 새 동작에 대응 테스트가 있는가? 테스트가 실제로 그 경계를
   검증하는가, 아니면 통과만 하는가? `tests/test_<module>_edge_cases.py`를 함께 본다.
6. **문서 일치.** `CLAUDE.md`의 아키텍처 서술이 현재 패키지 목록과 맞는가?

## 6. 지적의 한도

- **결함은 최대 5개.** 넘치면 파급이 큰 순으로 5개만 쓰고 나머지는 한 줄 목록으로 남긴다.
- **선택 사항은 최대 3개.** 이건 협상 대상이 아니다. 선택 사항이 결함보다 많은 리뷰는
  신뢰를 잃는다.
- 같은 원인에서 파생된 지적은 **하나로 묶는다.** 한 줄씩 쪼개 개수를 늘리지 않는다.

## 7. 코드를 고치지 않는다

발견만 하고 보고한다. **수정은 사용자의 판단이다.** 고칠 방향을 제안하는 것은 좋지만,
파일을 편집하지 않는다. 테스트를 추가하지도 않는다.

예외 없다. "명백한 오타라 그냥 고쳤다"도 하지 않는다. 리뷰어가 코드를 만지면 리뷰 결과와
변경이 뒤섞여 사용자가 무엇을 검토해야 하는지 알 수 없게 된다.

## 8. 보고

심각도 순으로 정렬한다. 서론 없이 결론부터 쓴다.

```
## 결론
<머지 가능 / 결함 N건 — 한 문장>

## 결함
1. `파일:줄` — 무엇이 문제인가
   재현: <명령>
   결과: <실제 출력>
   기대: <어떻게 됐어야 하는가>

## 의심
- `파일:줄` — 무엇에 기대고 있는가, 그 전제가 깨지는 조건

## 선택 사항
- 한 줄씩

## 확인했고 문제 없던 것
- 무엇을 봤는지 짧게 나열 (리뷰 범위를 사용자가 가늠할 수 있게)
```

마지막에 **실행한 검증 명령과 그 결과**를 남긴다. 리뷰를 재현할 수 있어야 한다.
