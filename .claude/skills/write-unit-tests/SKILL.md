# 유닛 테스트 작성

목표는 커버리지 숫자를 올리는 게 아니라 **기존 테스트 옆에 놓았을 때 누가 썼는지
구분되지 않는 테스트**를 꼭 필요한 만큼 쓰는 것이다.

이 기준이 중요한 이유: 테스트 파일은 사람이 반복해서 읽는 문서다. 스타일이 튀는 테스트가
섞이면 읽는 사람은 "왜 이건 다르지?"에 매번 주의를 뺏긴다. 그리고 한 번에 30개씩 쏟아진
테스트는 검토되지 않고 통째로 지워진다. 적게 쓰고 각각을 설명 가능하게 만드는 편이
실제로 남는다.

## 1. 쓰기 전에 읽는다

- **대상 소스 파일** — 검증할 동작과 분기를 파악한다.
- **`tests/`의 기존 테스트 파일** — 스타일의 최종 근거다. 이미 커버된 케이스도 여기서
  파악한다.
- **`CLAUDE.md`** — 저장소 수준 규칙.
- **`pyproject.toml`** — 러너와 의존성.

아래 2절은 이 스킬을 쓴 시점의 저장소를 기록한 것이다. **실제 파일과 어긋나면 실제
파일을 따르고, 어긋났다는 사실을 보고에 남긴다.** 문서보다 코드가 최신이다.

대상이 지정되지 않았으면 `git status`와 `git diff`로 최근 변경된 소스를 확인해 후보를
좁히고, 무엇을 테스트할지 먼저 알린 뒤 작성한다.

## 2. 이 저장소의 확정된 규칙

### 실행

```bash
uv run pytest                                     # 전체
uv run pytest tests/test_calculator.py::test_add  # 단일
```

`src/` 레이아웃이라 `vibe_coding` import는 `.venv`의 editable 설치(`vibe_coding.pth`)를
통해서만 해석된다. `.venv`를 활성화하지 않은 맨 `pytest`는 `ModuleNotFoundError`로
실패한다 — 이건 테스트 결함이 아니라 실행 방법 문제다.

### 파일 배치

- happy path → `tests/test_<module>.py`
- 엣지케이스 → `tests/test_<module>_edge_cases.py`

나누는 이유는 실패했을 때 **파일 이름만으로 기본 계약이 깨진 건지 경계 처리가 깨진
건지** 구분하려는 것이다. 새 모듈이라 두 파일이 다 없다면 happy path 파일부터 만든다.

### import

```python
from vibe_coding import Calculator
import pytest
```

최상위 패키지에서 import한다. `vibe_coding.calc.calculator`처럼 깊은 경로로 파고들지
않는다. 프로젝트 import가 먼저, `import pytest`가 다음 — 기존 두 파일이 모두 이
순서다(일반적인 PEP 8 순서와 반대지만 저장소 스타일이다).

대상이 새 모듈이면 최상위 import가 되는지 먼저 확인한다. `src/vibe_coding/<pkg>/__init__.py`와
`src/vibe_coding/__init__.py` 양쪽에서 재노출돼야 한다. 재노출이 빠져 있으면 깊은 경로
import로 우회해서 테스트를 통과시키지 말고, **재노출이 빠졌다고 보고한다.** 우회하는
순간 저장소가 기대하는 평탄한 import 경로가 조용히 깨진다.

### 테스트 함수 형태

```python
# Calculator Tests

def test_add():
    """더하기 테스트"""
    calc = Calculator()

    assert calc.add(2, 3) == 5
```

- 파일 맨 위에 `# <Class> Tests` / `# <Class> Edge Case Tests` 주석 한 줄.
- 클래스로 묶지 않는 평면 구조: `def test_<behavior>():`
- docstring은 한국어 한 줄, "~ 테스트"로 끝난다. 엣지케이스는 **무엇이 특수한지**를
  이름과 docstring 양쪽에 드러낸다 (`test_divide_by_zero` → `"""0으로 나누기 테스트"""`).
- 대상 객체를 매 테스트에서 새로 만들고, 빈 줄 하나 뒤에 assert를 쓴다. 준비와 검증이
  눈으로 갈린다.
- 픽스처·`setup` 함수·모듈 전역 인스턴스를 쓰지 않는다. 테스트 간 상태를 공유하지 않는다.

### 검증 형태

- 리터럴 기대값으로 쓴다: `assert calc.add(2, 3) == 5`. 계산식을 그대로 다시 쓴 assert나
  "올바르게 동작한다" 식의 모호한 검증은 아무것도 고정하지 못한다.
- 예외는 `pytest.raises`로 **타입까지** 고정한다.
- `pytest.approx`는 부동소수점 비교에만 쓴다.
- `@pytest.mark.parametrize`를 쓰지 않는다. 기존 테스트에 없는 형태이기도 하고, 경계마다
  이름 있는 함수를 두는 편이 실패했을 때 원인 파악이 빠르다.
- 소스에 타입 힌트가 없고 린터·포매터도 설정돼 있지 않다. 테스트에 새로운 스타일이나
  도구를 들이지 않는다.

## 3. 무엇을 쓸지 고른다 — 절제가 핵심이다

### happy path

공개 메서드마다 대표 입력 1개. **이미 있으면 다시 쓰지 않는다** — 기존 파일을 먼저 읽고
공백만 채운다.

### 엣지케이스

후보를 이 순서로 찾는다:

1. **경계값** — 0, 음수, 1, 빈 값. 부호가 바뀌는 지점, 조건문의 경계.
2. **예외 경로** — 어떤 입력이 무슨 예외를 던지는가.
3. **부동소수점과 반환 타입** — 정수와 실수의 동작이 갈리는 연산, `divide`가 항상 float를
   내는지 같은 것.
4. **타입 다형성** — 타입 힌트가 없는 코드는 의도치 않은 타입도 받는다. 그 동작이 계약인지
   판단한다.

**쓰지 않을 것을 가려내는 게 절반이다:**

- **이미 커버된 각도를 반복하지 않는다.** 이 저장소는 파이썬 연산자 위임 동작 자체를
  계약으로 보고 `test_add_with_strings`, `test_multiply_with_list` 같은 테스트를 이미
  갖고 있다. 같은 성격의 테스트를 하나 더 얹는 건 가치가 거의 없다. 아직 아무도 확인하지
  않은 결정 지점을 찾는다.
- **소스가 명시적으로 다루지 않는 미정의 동작을 고정하지 않는다.** 지금 우연히 통과하는
  동작에 테스트를 박으면 리팩터링만 막는다. 이런 후보는 쓰지 말고 보고에 남긴다.

### 양의 한도

- 엣지케이스는 **모듈당 최대 5개.** 후보가 넘치면 실제 결함으로 이어질 가능성이 높은
  순으로 5개만 쓰고, 나머지는 **작성하지 말고 보고에 남긴다.** 더 필요하면 사용자가
  요청할 것이다.
- **테스트 1개 = 케이스 1개.** 하나의 함수에 여러 경계를 몰아넣으면 실패했을 때 이름만
  보고 어디가 깨졌는지 알 수 없다. (기존 `test_reuse_same_instance`처럼 여러 호출을
  이어 하는 것 자체가 검증 대상인 경우는 예외다.)

## 4. 소스 코드는 고치지 않는다

경계를 파고들면 실제 결함을 만나게 된다. 관찰한 동작이 의도된 것인지 혼자 단정하지 말고
이렇게 나눈다:

- **명백히 잘못된 동작** (틀린 계산 결과, 조용한 데이터 손상, 엉뚱한 예외 타입) —
  테스트를 그 동작에 맞춰 통과시키지 않는다. 작성을 멈추고 재현 입력·실제 결과·기대
  결과를 보고한다. **버그를 고정한 테스트는 버그보다 나쁘다.** 고칠지 말지는 사용자가
  정한다.
- **놀랍지만 타당한 동작** (파이썬 의미론에서 자연스럽게 따라오는 것) — 테스트로 고정하되
  그것이 의도적 선택임을 docstring에서 드러낸다.
- **판단이 갈리는 경우** — 쓰지 말고 보고한다.

## 5. 실행해서 통과를 확인한다

`uv run pytest`를 실행한다. **실행해서 통과를 확인하지 않은 테스트는 결과로 내놓지
않는다.**

실패하면 원인을 가른다. 테스트가 틀렸으면 고치고, 소스가 틀렸으면 4절대로 보고한다.

새로 쓴 엣지케이스가 처음부터 전부 통과했다면 정말 경계를 건드렸는지 다시 본다. 통과가
목표가 아니다.

## 6. 보고

- 작성한 테스트 목록 — 파일별로, 각 1줄. 엣지케이스는 **어떤 경계를 검증하는지** 명시.
- `uv run pytest` 결과 (통과/실패 개수).
- 한도나 판단 보류로 일부러 생략한 후보와 그 이유.
- 발견한 소스 결함 — 재현 입력, 실제 결과, 기대 결과.
- 2절의 기록과 실제 저장소가 어긋난 부분 (있다면).
