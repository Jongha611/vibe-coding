# 유닛 테스트 작성

목표는 커버리지 숫자를 올리는 게 아니라 **기존 테스트 옆에 놓았을 때 누가 썼는지
구분되지 않는 테스트**를 꼭 필요한 만큼 쓰는 것이다.

이 기준이 중요한 이유: 테스트 파일은 사람이 반복해서 읽는 문서다. 스타일이 튀는 테스트가
섞이면 읽는 사람은 "왜 이건 다르지?"에 매번 주의를 뺏긴다. 그리고 한 번에 30개씩 쏟아진
테스트는 검토되지 않고 통째로 지워진다. 적게 쓰고 각각을 설명 가능하게 만드는 편이
실제로 남는다.

## 1. 쓰기 전에 읽는다

- **대상 소스 파일** — 검증할 동작과 분기를 파악한다.
- **기존 테스트 파일** — 스타일의 최종 근거다. 이미 커버된 케이스도 여기서 파악한다.
- **CLAUDE.md** — 저장소 수준 규칙.
- **pyproject.toml / setup.cfg / tox.ini / Makefile** — 러너와 의존성.

대상이 지정되지 않았으면 `git status`와 `git diff`로 최근 변경된 소스를 확인해 후보를
좁히고, 무엇을 테스트할지 먼저 알린 뒤 작성한다.

## 2. 저장소에서 규칙을 뽑아낸다 — 추측하지 않는다

이 스킬은 특정 저장소를 전제하지 않는다. 아래를 **실제 파일에서 확인해 확정한 뒤**
쓰기 시작한다. 확인 없이 일반적인 파이썬 관례를 들이대면 그게 곧 스타일 오염이다.

### 실행 명령

락파일과 설정에서 판단한다.

| 근거 | 명령 |
|---|---|
| `uv.lock` | `uv run pytest` |
| `poetry.lock` | `poetry run pytest` |
| `Pipfile.lock` | `pipenv run pytest` |
| 없음 / venv 활성 | `pytest` |

`Makefile`이나 CI 설정(`.github/workflows/`)에 테스트 타깃이 있으면 그쪽이 정답이다.
`src/` 레이아웃이면 패키지는 editable 설치를 통해서만 import된다 — 러너를 거치지 않은
맨 `pytest`가 `ModuleNotFoundError`로 죽는 건 테스트 결함이 아니라 실행 방법 문제다.

### 파일 배치와 이름

기존 테스트 디렉터리의 실제 파일명을 근거로 삼는다. 흔한 형태는 이 둘이다.

- `tests/test_<module>.py` — happy path
- `tests/test_<module>_edge_cases.py` — 엣지케이스

파일을 나누는 이유는 실패했을 때 **파일 이름만으로 기본 계약이 깨진 건지 경계 처리가
깨진 건지** 구분하려는 것이다. 저장소가 이미 다른 규칙(예: `<module>_test.py`,
클래스 기반 그룹핑)을 쓰고 있으면 그쪽을 따른다. 테스트가 하나도 없는 새 저장소라면
위 두 파일부터 만든다.

### import 경로

기존 테스트가 어떤 깊이로 import하는지 그대로 따른다. 패키지가 최상위에서 재노출되고
있으면 최상위에서 import한다 — 재노출이 있는데도 깊은 내부 경로로 파고들지 않는다.

대상이 새 모듈이면 **의도된 import 경로가 실제로 열려 있는지 먼저 확인한다.**
재노출이 빠져 있으면 깊은 경로 import로 우회해서 테스트를 통과시키지 말고,
**재노출이 빠졌다고 보고한다.** 우회하는 순간 저장소가 기대하는 import 경로가
조용히 깨진다.

### 테스트 함수 형태

기존 파일에서 다음을 그대로 베낀다. 하나라도 다르면 그 테스트는 튄다.

- 파일 상단 주석 유무와 형식
- 함수 이름 규칙 (`test_<behavior>`)
- **docstring의 언어와 형식** — 한국어 저장소면 한국어로 쓴다. 이건 취향이 아니라
  일관성 문제다.
- 클래스 그룹핑 여부, 픽스처 사용 여부
- 준비와 검증 사이의 빈 줄 같은 사소한 배치

기존 테스트가 픽스처나 `setup`을 쓰지 않는다면 새 테스트에도 넣지 않는다. 대상 객체를
매 테스트에서 새로 만들고 테스트 간 상태를 공유하지 않는 편이 기본값으로 안전하다.

### 검증 형태

- 리터럴 기대값으로 쓴다: `assert calc.add(2, 3) == 5`. 계산식을 그대로 다시 쓴 assert나
  "올바르게 동작한다" 식의 모호한 검증은 아무것도 고정하지 못한다.
- 예외는 `pytest.raises`로 **타입까지** 고정한다.
- `pytest.approx`는 부동소수점 비교에만 쓴다.
- **기존 테스트에 없는 도구를 새로 들이지 않는다.** `@pytest.mark.parametrize`,
  `unittest.mock`, 새 플러그인 의존성 모두 해당한다. 경계마다 이름 있는 함수를 두는 편이
  실패했을 때 원인 파악이 빠르다.
- 소스에 타입 힌트가 없고 린터·포매터도 없는 저장소라면 테스트에만 새 스타일을
  들이지 않는다.

## 3. 무엇을 쓸지 고른다 — 절제가 핵심이다

### happy path

공개 함수·메서드마다 대표 입력 1개. **이미 있으면 다시 쓰지 않는다** — 기존 파일을 먼저
읽고 공백만 채운다.

### 엣지케이스

후보를 이 순서로 찾는다:

1. **경계값** — 0, 음수, 1, 빈 값. 부호가 바뀌는 지점, 조건문의 경계.
2. **예외 경로** — 어떤 입력이 무슨 예외를 던지는가.
3. **부동소수점과 반환 타입** — 정수와 실수의 동작이 갈리는 연산, 나눗셈이 항상 float를
   내는지 같은 것.
4. **타입 다형성** — 타입 힌트가 없는 코드는 의도치 않은 타입도 받는다. 그 동작이 계약인지
   판단한다.

**쓰지 않을 것을 가려내는 게 절반이다:**

- **이미 커버된 각도를 반복하지 않는다.** 저장소가 파이썬 연산자 위임 동작을 이미
  테스트로 고정해 뒀다면 같은 성격의 테스트를 하나 더 얹는 건 가치가 거의 없다. 아직
  아무도 확인하지 않은 결정 지점을 찾는다.
- **소스가 명시적으로 다루지 않는 미정의 동작을 고정하지 않는다.** 지금 우연히 통과하는
  동작에 테스트를 박으면 리팩터링만 막는다. 이런 후보는 쓰지 말고 보고에 남긴다.

### 양의 한도

- 엣지케이스는 **모듈당 최대 5개.** 후보가 넘치면 실제 결함으로 이어질 가능성이 높은
  순으로 5개만 쓰고, 나머지는 **작성하지 말고 보고에 남긴다.** 더 필요하면 사용자가
  요청할 것이다.
- **테스트 1개 = 케이스 1개.** 하나의 함수에 여러 경계를 몰아넣으면 실패했을 때 이름만
  보고 어디가 깨졌는지 알 수 없다. (여러 호출을 이어 하는 것 자체가 검증 대상인 경우는
  예외다.)

## 4. 소스 코드는 고치지 않는다

경계를 파고들면 실제 결함을 만나게 된다. 관찰한 동작이 의도된 것인지 혼자 단정하지 말고
이렇게 나눈다:

- **명백히 잘못된 동작** (틀린 계산 결과, 조용한 데이터 손상, 엉뚱한 예외 타입) —
  테스트를 그 동작에 맞춰 통과시키지 않는다. 작성을 멈추고 재현 입력·실제 결과·기대
  결과를 보고한다. **버그를 고정한 테스트는 버그보다 나쁘다.** 고칠지 말지는 사용자가
  정한다.
- **놀랍지만 타당한 동작** (파이썬 의미론에서 자연스럽게 따라오는 것) — 테스트로 고정하되
  그것이 의도적 선택임을 docstring에서 드러낸다.
- **판단이 갈리는 경우** — 쓰지 말고 보고한다.

예외는 **TDD 흐름으로 새 기능을 만드는 중일 때**다. 이때는 아직 없는 코드를 향해
실패하는 테스트를 먼저 쓰는 것이 정상이며, 그 실패(Red)를 확인한 뒤 구현으로 넘어간다.
이 플러그인의 훅이 그 순서를 강제하고 Red 여부를 알려준다.

## 5. 실행해서 통과를 확인한다

2절에서 확정한 명령으로 테스트를 실행한다. **실행해서 통과를 확인하지 않은 테스트는
결과로 내놓지 않는다.**

실패하면 원인을 가른다. 테스트가 틀렸으면 고치고, 소스가 틀렸으면 4절대로 보고한다.

새로 쓴 엣지케이스가 처음부터 전부 통과했다면 정말 경계를 건드렸는지 다시 본다. 통과가
목표가 아니다.

## 6. 보고

- 작성한 테스트 목록 — 파일별로, 각 1줄. 엣지케이스는 **어떤 경계를 검증하는지** 명시.
- 테스트 실행 결과 (통과/실패 개수).
- 한도나 판단 보류로 일부러 생략한 후보와 그 이유.
- 발견한 소스 결함 — 재현 입력, 실제 결과, 기대 결과.
- 2절에서 확정한 규칙이 저장소 문서(CLAUDE.md 등)와 어긋난 부분 (있다면).
